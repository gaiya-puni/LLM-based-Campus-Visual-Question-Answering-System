# 可行性与安全性评估：候选新功能与升级方向

> 评估日期：2026-10-10
> 评估对象：本轮审查中提出的 **8 项可新增功能**（§2~§9）+ **4 项中长期升级方向**（§12）
> 结论口径：**能做到什么程度、要付什么代价、有什么风险**——不是愿望清单
> 所有"现有数据是否支持"的判断都附实测数字，取数脚本见文末《取数方式》

---

## 0. 一句话结论

**8 项里 1 项已落地（图片问答），3 项属于"已有基础、补一段就成"（行程真实算路、数据校验器、评测体系化），2 项依赖外部模型但风险可控（reranker、可观测性），1 项（用户共建自动化）技术与设施已齐备但**必须保留人工闸门**，1 项（无障碍/移动端）成本主要在人工核对。**

**4 项升级方向里，没有一项卡在"难"，全部卡在"前置条件"**：独立成包卡在多校 schema 对齐，矢量边界卡在边界数据（且运行时至今仍是纯半径判定），智能体化卡在"不能破坏被测试锁定的确定性路由"，小程序卡在重写成本与"二次展示认养人信息的同意范围"。**先补前置，再谈升级。**

- 8 项可新增功能的建议落地顺序见 §10；
- 4 项升级方向的结论、依赖顺序与优先级见 §12。

## 2. 图片问答（本轮已落地）

### 可行性
后端链路早已写好却无人调用，本轮把它接进 `/api/chat` 并补上前端入口：

- 后端：`parse_attachments`（张数/类型/体积三重校验）→ `extract_places_from_photo`（视觉模型抽图中可读地名）→ `match_pois_by_names`（命中校园 POI）→ 写入 system prompt + 地图打点 → `build_llm_messages`（附件只并入最后一条用户消息）。
- 前端：新增 `src/components/imageAttach.ts`（点击/拖拽/粘贴/拍照 + Canvas 等比压缩）与 `chatbot.vue` 输入区改造。
- 体积上限四处口径已统一：单张 4MB、最多 2 张、允许 jpeg/png/webp、全局请求体上限抬高到 12MB 并对超限返回 **JSON 413**（此前默认 1MB，任何稍大图片都会被 Flask 直接拒绝）。

### 安全与可靠性（均为代码级事实）
- 图片**不落盘**，日志只记张数与体积，不记内容；
- mime 必须与 dataURL 前缀一致才接受，避免"声明 png 实际 jpeg"这类绕过；
- 图中线索抽取失败（超时/非 JSON/HTTP 错误）**只返回空列表，不影响主回答**，已有测试锁定；
- **未配置视觉模型时不把图片转发给上游**（纯文本模型收到 `image_url` 会直接报错），改为按能力如实回答"本部署未启用图片理解"；
- 历史轮次不回传 base64，避免 token 与带宽失控。

### 验证证据
- 21 个单元/集成测试（`test_chat_vision.py`）：附件校验 10 项、多模态消息构造 3 项、能力文案 2 项、端到端接线 6 项。
- 浏览器实测（Playwright）：注入 3 张图 → 仅保留 2 张并提示"已忽略超出上限的 1 张"；1.43MB 原图被压到 **283KB**；粘贴、拖拽、拖拽高亮均生效；请求体确实携带 2 条 `image/jpeg` 附件；用户气泡回显缩略图；本机（未配视觉模型）回答为"本部署未启用图片理解…"的如实降级文案。

### 剩余依赖
需要两个视觉入口之一：`VISION_API_KEY`（独立视觉模型，推荐）或 `VISION_ENABLED=true` + 所选服务商标记为支持视觉。`/api/health` 已新增 `vision` 字段供前端提示（本机实测为 `false`）。

## 3. 检索质量再上一层：reranker / 查询改写 / 多轮指代消解

### 可行性：中
现有设施齐备（句向量 + 余弦相似度 + 关键词回退 + 场景语料 + 50 例评测集），加一层 rerank 或查询改写都是**加法**，不动既有链路。

### ⚠️ 前置问题：现有评测集区分不出两种检索后端

- 本地 `.env` 设为 `SEMANTIC_ENABLED=false`（省内存、启动快）。**两种模式本机都能跑通**：
  - 规则路径：`passed=50/50 accuracy=100.0%`
  - 嵌入路径（`SEMANTIC_ENABLED=true`）：`semantic backend {... 'reason': 'ok'}`，`passed=50/50 accuracy=100.0%`
- 也就是说**当前这 50 例对两套后端都是满分**——它证明不了"加了向量检索更好"，也无法为 reranker 提供一个能看出差异的基线。

> 勘误（2026-10-10 追加）：本节初稿曾写"本机 `SEMANTIC_ENABLED=true` 会崩溃、退出码 `0xC0000005`"。
> 复测为**误报**：`sentence_transformers` 导入、`BAAI/bge-small-zh-v1.5` 加载与编码均正常
> （`encode OK, dim = 512`），评测脚本退出码为 0。

**结论：做 reranker 之前要先让评测集"有区分度"**（更难、更贴近真实问句、并引入排序指标），
否则调完无法判断是变好还是变坏。

### 安全风险
- 新增模型 = 新增下载源与供应链面（需固定版本与校验）；
- 延迟与成本上升，必须保持"模型/依赖缺失即回退关键词规则"的既有契约（`SEMANTIC_ENABLED=auto`），否则一次环境问题会让问答整体不可用；
- 查询改写引入把用户问句二次外发（若用远端 LLM），需与现有 `LLM_PROVIDER` 口径一致并避免记录用户原文。

## 4. 行程规划接高德真实步行算路

### 可行性：高
三块拼图都已存在：
- 后端已有 `AMAP_WEB_SERVICE_KEY` 并用于地理编码/POI 搜索；
- 前端 `index.html` 已加载 `AMap.Walking` 插件，`chatbot.vue` 已有 `doRoute()` 步行路线绘制；
- 目前唯一的硬伤是**两套距离口径并存**（面板显示高德真实算路、大模型文案基于后端直线估值），项目文档已把它列入已知限制。

改成后端统一调用 Web 服务算路，可一并消除这个矛盾。

### 安全与成本
- 每次行程会多 N 次外部调用 → **必须加缓存 + 配额保护**，并保留失败时回退直线估值的降级路径（不能让高德抖动导致行程不可用）；
- 浏览器 Key 与 Web 服务 Key 是两把不同的 Key、用途与配额限制都不同，**不得混用**（现有文档已明确）；
- 算路参数来自用户输入（起点/终点），必须做坐标合法性校验（项目已有 NaN/越界防护，需覆盖到新参数）。

## 5. 用户共建闭环自动化（高置信度自动并入 + 抽查）

### 可行性：中高
基础设施已相当完整：`userdata_store.py`（626 行：JSONL 事件流 + 派生清单 + 原子写 + 脱敏 + 聚合去重 + 导出 POI 契约）、`place_extraction.py`（280 行：60+ 通名规则 + LLM 兜底）、审核页与导出接口、以及 `publish.py`（差异计划、哈希校验、双备份、失败回滚）。

### 安全风险（本项风险最高，必须保留人工闸门）
- **误并入会被地图打点、推荐、热度三处同时放大**（项目文档已记录这一教训）；
- 采集全程是旁路且已有"不改回答、不加延迟"的测试锁定，自动化绝不能破坏这一点；
- 建议的安全形态：高置信度条目**仅生成待发布差异计划**，仍需一次人工确认；发布走既有 `publish.py` 的哈希校验 + 备份 + 回滚；对自动并入条目做**抽样复核 + 可一键回滚**；并记录来源与审核人。
- 用户上报内容属个人贡献，**只存本机、不入库**（现有 `.gitignore` 已覆盖 `webapp/backend/userdata/*`），自动化不得改变这一约束。

## 6. 数据治理与 POI 校验器

### 可行性：高，且收益明确
实测数据质量已很好（0 缺坐标、0 越界、4 组重复坐标），所以校验器的成本很低：把现有"靠人肉核对"的判断固化成 `scripts/validate_pois.py`，挂进 CI。

建议规则：缺坐标 / 零坐标 / NaN、坐标越界（`campus_at()` 为 None）、重复坐标（同点多条）、点位名与类别必填、**坐标系标注缺失**。

### 实测缺口
POI 只有 `source` 字段（fangnong / amap_place_text / amap_place_around / manual_*），**没有独立的 `crs` 字段**。跨源混用 GCJ-02/WGS84 只能靠约定与生成器内部逻辑，无法在数据层自动发现。建议为 POI 增加 `crs`、`updatedAt`、`审核人`；生成器侧继续按现有约定（网页 JSON-LD 按 WGS84 处理，绝不冒充高德坐标）。

### 安全
纯只读校验，无安全风险；唯一注意点是校验器不要顺手"自动修复"坐标——那会把一次静默错误固化进正式资产。

## 7. 可观测性（结构化日志 / 耗时 / token / 分层健康检查）

### 可行性：高
已有基础：`/api/health` 返回 `status`、`database`，本轮新增 `vision`；启动时打印当前服务商与模型名（且刻意不打印密钥）；已有 `rate_limit` 装饰器与中文日志。

### 缺口与建议
缺口：无请求耗时统计、无上游 token/配额计数、无聚合视图、上游调用（30s/45s 超时）失败率不可见。

建议**不引入重依赖**（不急着上 Prometheus），先做三件低成本的事：
1. 轻量中间件记录 `(endpoint, status, duration_ms)`，滚动写本地 JSONL；
2. 统计上游 LLM 调用的 token 数与失败原因，落同一份日志；
3. `/api/health` 继续按"能力"分层暴露（DB / 语义索引 / 视觉），让排障一眼定位。

### 安全
日志是隐私高风险面：**绝不能记录用户问句原文、图片内容或 API Key**。现有采集旁路的脱敏口径（日志只记张数与体积、不记内容）应被沿用为通用规则。

## 8. 无障碍与移动端

### 可行性：中
本轮已修正 `index.html` 的 `lang`（`zh-CN`）、标题（`ECNU·校园可视可答系统`）、图标与页面描述；移动端拍照已用文件输入的原生 `capture` 实现，不引入新依赖。

仍缺：`aria` 标注、键盘导航（当前发送依赖回车与按钮，地图交互无键盘路径）、颜色对比度核查、小屏地图与热图面板的布局验证。

### 安全
无安全风险，成本集中在人工核对与样式调整；建议与"移动端导览"场景一起做，避免为无障碍单独改一遍布局。

## 9. 评测体系化（Recall@k / MRR / nDCG + CI 门槛）

### 可行性：高，但**必须先补"可测性"**
已有：50 例语义检索评测（**规则路径与嵌入路径都是 100%**）、`evaluate_scene_heatmaps.py`（自带"无标注不能下结论"的声明）、21 个测试文件 / 6323 行 / 393 通过。

三个实测缺口：
1. **评测集没有区分度**：50 例对规则路径与嵌入路径都是满分（`50/50 accuracy=100.0%` 两种模式各测一次），
   既证明不了向量检索的增益，也无法用来评估 reranker 的改动是好是坏；
2. **热图评价没有人工标注**：脚本明确写了"不能据此宣称 SAKDE 推荐更准确"，目前只有技术对照数据（相关系数 -0.09…0.81）；
3. **没有排序指标**：50 例只判"给没给对"，没有 Recall@k / MRR / nDCG，无法度量 Top 排序质量。

建议路径：加难例并把两种后端都跑出可见差异 → 补 20~50 条热图人工标注 → 把指标（Recall@5、MRR、nDCG@5）与既有 50 例一起纳入 CI 门槛。

## 10. 结论与优先级

| 优先级 | 功能 | 结论 | 主要代价 | 主要风险 |
|---|---|---|---|---|
| **P0** | 图片问答 | ✅ **已落地** | 已完成 | 需配视觉 Key 才能看到真实效果 |
| **P0** | 评测体系化（先补可测性） | 高可行 | 加难例 + 补约 30 条标注 + 排序指标 | 现有 50 例两种后端都满分，不扩就没有度量能力 |
| **P1** | 数据治理与 POI 校验器 | 高可行、低成本 | 约 1 天（规则 + CI） | 校验器不应自动改写坐标 |
| **P1** | 行程真实步行算路 | 高可行 | 后端接 Web 服务 + 缓存 | 配额与失败降级 |
| **P1** | 可观测性 | 高可行 | 轻量中间件 + JSONL | 日志绝不能记用户原文与密钥 |
| **P2** | 用户共建自动化 | 中高可行 | 阈值 + 抽查 + 回滚 | **误并入被三处放大**，闸门不可省 |
| **P2** | 无障碍与移动端 | 中 | 人工核对 + 样式 | 无 |
| **P3** | reranker / 查询改写 / 指代消解 | 中（被前置问题卡住） | 新模型 + 延迟 | 供应链、延迟、必须保留关键词回退 |

## 11. 贯穿所有功能的共同前提

1. **认养人个人信息必须原样保留**。植物认养人的姓名、单位与寄语，是经本人同意在华东师范大学小程序「芳秾」及官网上公开的内容。本项目引用时**不做删改、不做脱敏、不移出版本库**；`scripts/sanitize_public_data.py` **不应**作为常规清理步骤执行。
2. **密钥脱敏约定不变**：任何提交前跑 `python scripts/check_publication.py`，真实凭据只放本机 `.env`。
3. **新增外部依赖一律走"缺失即优雅降级"**：向量模型缺失回退关键词、视觉模型缺失如实告知、算路失败回退直线估值、搜索服务未配置只提示不中断。
4. **新增能力不得把个人数据带出**：日志、缓存、上报都只记录可公开的元信息。

## 12. 升级方向可行性评估

> §2~§9 评的是"**能加什么功能**"，本章评的是"**往哪走**"。两张优先级表并列、互不冲突：
> 功能表回答"下一批做什么"，方向表回答"这套东西两年后长成什么形状"。
> 口径与前 11 章完全一致：可行性 / 安全与风险 / 依赖与成本 / 结论与优先级，结论一律附实测证据。

### 12.1 从"一个系统"到"一条流水线"：把生成器独立成可安装的包

**可行性：中高，但被两条前置卡住。**

已经具备的（比预想的好）：

- `tools/campus_generator/cli.py` **已存在，且有 8 个子命令**：`profile` / `validate` / `normalize` /
  `harvest` / `harvest-amap` / `harvest-web` / `build` / `check`。
- 其中 `profile` 子命令（`cli.py` 的 `cmd_profile`）能直接生成校区档案模板，参数为
  `--school-id --school-name --campus-name --campus-slug --lng --lat --trust-radius --coordinate-system --output`。
  也就是说 `campuses/profiles/*.json` 这类档案**可以由 CLI 重新生成**，不是硬阻塞。
- 生成器自带测试且全绿：`python -m pytest tools/campus_generator -q` → **104 passed / 1 skipped**。

尚未具备的（真正的阻塞）：

1. **全仓没有任何打包元数据**：无 `setup.py` / `setup.cfg` / `MANIFEST.in` / `*.egg-info`；
   且 `pyproject.toml` **故意不声明 `[project]`**（文件内注释写明：本仓库是"应用 + 工具包"的仓库，
   声明 `[project]` 会改变 `pip install -e .` 的安装语义）。→ 结论：独立成包是**被刻意搁置**的，
   不是"顺手就能做"。
2. **多校 schema 未对齐**：`profile.runtime_config()` 的产出结构与现行 `campuses.json`
   （含 `schools` 表、每校区 `school` 外键、`brand`）需要核对；`campus_config.check_consistency`
   对多校有强校验，**不先对齐就重跑资产生成会丢字段并挂在一致性检查上**（详见 `HANDOVER.md` §7.2）。
3. **只支持单进程本地运行**：任务管理器不跨进程共享任务目录，包装成常驻服务前必须先解决。

**安全与风险**：

- 打包与分发**绝不能把 `data/` 目录一起带走**——那里含认养人的姓名、单位与寄语（§11 第 1 条）。
  工具包应只带代码与契约，数据由使用者按文档自备。
- 声明 `[project]` 会改变安装语义，而当前 `server.py` 与测试依赖
  "仓库根目录 + `webapp/backend` 都在 `sys.path`"这一现状，改之前要先评估影响面。

**依赖与成本**：先对齐多校 schema（否则产不出与现有三校区一致的产物）→ 再划打包边界
（哪些资产进包、哪些留在应用）→ 最后才是 `[project]`、构建配置与使用文档。

**结论与优先级：P2**。价值高（把项目从"一个网站"升级为"一套方法论 + 工具"），
但必须排在 12.2 的边界数据与多校 schema 之后；前置未补齐就动手，产出的包跑不出与现有校区一致的结果。

### 12.2 用正式矢量边界替换"可信半径降级"

**可行性：代码已就绪，缺的是数据 + 一次跨切面接线。这是"两步走"，不是"换个判定方式"。**

**第一步：生成器侧的多边形能力已完整**（`tools/campus_generator/boundary.py`）：

- `validate_polygon`（L72）只接受 GeoJSON **Polygon 外环**（明确拒绝 holes / MultiPolygon），
  并要求环闭合、至少 3 个不同顶点、面积非零、**不自交**、不超过 2000 个点；
- `point_relation`（L140）/ `point_in_polygon`（L148）/ `boundary_hash`（L153）；
- `validate_campus_boundary`（L159）在存在 `boundary` 时强制要求 `boundarySource`、
  `boundaryConfidence` ∈ [0,1]、`coordinateSystem` 必须为 **GCJ-02**，且 `center` 必须落在边界内。

**但边界数据缺失**：`webapp/backend/campuses.json` 三个校区目前只有 `center` + `trustRadiusM`
（普陀 1300 / 闵行 2200 / 交大闵行 1800），**没有任何 `boundary` 字段**。

**第二步：运行时仍是纯半径**。`campus_config.campus_at()`（定义于 L307）按 `trustRadiusM` 做圆判定，
未使用多边形；而它的调用方是跨切面的：`chat_api.py` ×3、`userdata_api.py` ×1、
`campus_config.py` ×2（内部）、`test_campus_config.py` ×1 —— **共 7 处**。
接线时必须**保留"无边界时按半径降级"的既有行为**，否则尚未录入边界的校区会立刻失去成员判定。

**安全与风险**：

- 坐标系混用是本项目已经踩过的坑（生成器明确要求"网页 JSON-LD 坐标按 WGS84 处理、绝不冒充高德 GCJ-02"），
  因此边界数据**必须带来源与置信度**，并在入库前走 `validate_polygon` 的自交 / 面积 / 闭合校验——
  自交多边形会让"点在界内"的判定变得不可预测，进而影响问答点位与用户上报的归属。
- 边界收紧会把原本"在半径内、但在校界外"的点位判为无效（例如紧邻校门的马路对面商铺）。
  切换前应先跑一次新旧判定差异比对，确认不会把现有正式 POI 判出界外。

**依赖与成本**：硬依赖是**边界数据来源**（需校方或公开 GIS 的授权与核实，属人工与外部协调成本）；
数据到位后运行时接线本身是小改动，但要用"新旧判定差异报告 + 既有测试全绿"来验收。

**结论与优先级：P1**（收益明确、风险可控，但前置在数据）。

### 12.3 智能体化：把现有能力做成可被大模型编排的工具

**可行性：只能做"加法"，不能做"替换"。**

**为什么不能替换**：现在 `/api/chat` 是**确定性规则优先**架构——`chat_api.py` 的 `chat()` 里，
"指哪问哪（needle）→ 一日行程 → 场景热图"这些分支在**调用大模型之前就已经 return**，
只有走到最后才发一次 LLM 请求。这套优先级**被测试显式锁定**：

- `test_chat_itinerary.py`（11 个用例，其中 4 个专测路由优先级与起点来源）存在的目的就是锁
  "行程意图优先于针尖与机构位置查询"；
- `test_chat_needle.py`（13 个用例）锁针尖分支的触发条件；
- `test_recommendation_v2.py` 锁推荐回归。

把它换成"让模型决定调哪个工具"，等于**反转架构并让这批测试契约失效**。
而项目既有的设计立场是"**大模型只写文案，站点与顺序由确定性算法编排**"（`PROJECT_STATUS.md` §四），
这条立场正是行程功能可靠的原因。

**现状**：后端**零 tool calling**——全仓 `webapp/backend/` 检索 `tool_calls` / `function_call` / `tools=` 均无命中，
属彻底新建，没有半成品可复用。

**可落地的加法形态**：

1. **仅对复合问句**（一次问句里同时含多个意图，例如"下午哪适合自习，顺便推荐个能拍照的地方"）
   启用一个小规划器：由模型输出"调用哪些既有能力、按什么顺序"；其余问句**完全维持现状**；
2. 规划器的输出**只当作既有能力的选择器**，执行仍落回现有确定性链路；
3. 规划器不可用（未配密钥 / 超时 / 输出不合法）时，**无缝回退到现有确定性路由**。

**可参考的既有低成本范式**：`place_extraction.py` 的 `llm_extract`（L247）/ `parse_llm_places`（L211）——
默认 `batch` 模式**在线零调用**、判不出来的进队列，只有显式切 `inline` 才当场判一次。
规划器应沿用同样的"默认可关闭、失败不影响主链路"姿态。

**安全与风险**：

- **工具白名单 + 服务端二次校验**：模型给出的参数一律不可信（提示注入可诱导越权参数），
  所有入参必须走既有的清洗（有限值校验、校区范围校验）；
- **只读优先**：检索、热图、行程是只读能力，适合作为工具；
  而 `publish` / `review` / 数据并入这类**写操作绝不能交给模型自动触发**——
  现有的人工审核闸门 + 差异计划 + 哈希校验 + 回滚必须原样保留；
- **成本与延迟**：规划器多一次 LLM 调用，必须可关闭、带超时，并复用"缺失即降级"的既有契约。

**依赖与成本**：依赖 §9"评测体系化"提供**可度量的基线**——否则"智能体化后是否更好"无从判断；
同时依赖 §3 先把检索本身做稳，否则规划器只是在放大一个不稳定的召回。

**结论与优先级：P3**（方向正确，但必须等评测基线与检索质量就位，且只做加法）。

### 12.4 小程序与扫码导览

**可行性：拆成"重路径"与"轻路径"，两者成本差一个数量级。**

**重路径（微信小程序）成本极高**：

- 现有实现是 Vue 3 SPA + **高德地图 JavaScript API（Web 版）**，无法直接复用到小程序，
  需用 WXML 重写或整体迁到 uni-app / Taro；
- 小程序内使用高德需换**小程序 SDK**，Key 类型与配额策略与 Web 端**不同**，
  现有"浏览器 Key / Web 服务 Key"的两把钥匙约定要扩成三套；
- 上线需要小程序主体资质与平台审核。

**轻路径（推荐先做）**：给现有 Web 应用补**移动端响应式** + 二维码 / 分享入口。
代价小得多，且能立刻服务"新生与访客"这个真实场景。

**证据（移动端现状几乎是空白）**：`webapp/frontend/src` 共 44 个文件，全量检索
`touchstart|touch-action|isMobile|window.innerWidth` 仅 **1** 处命中，`@media` 仅 **9** 处
（合计 10 处，多为字号与间距微调），等于**没有做过移动端适配**。

**合规前置决策项（需用户或校方拍板，本评估不替其决定）**：
认养人的姓名、单位与寄语是**经本人同意**在校园小程序「芳秾」及官网上公开的内容。
把它搬到小程序或扫码页，属于**第二个公开渠道的二次展示**，是否落在同意范围内需要重新确认（§11 第 1 条）。
**这一点必须先有结论，再谈技术选型。**

**安全与风险**：

- 现有后端刻意关闭了摄像头权限（`flask_app.py` 的 `Permissions-Policy: camera=(), microphone=()`），
  移动端拍照走 `<input type="file" capture>` 的原生文件选择，不开放 `getUserMedia`。
  **迁移到小程序或新前端时必须保持这一收口**，不要为了"扫码即拍"而放宽；
- 扫码入口会带来公开可达的流量：既有的限流、审核令牌，以及"用户共建数据只存本机"的约束都要一并复核。

**依赖与成本**：轻路径**不依赖其它任何方向**，可独立开工；重路径依赖主体资质、
Key 体系扩充与整体重写，不建议在当前阶段启动。

**结论与优先级：轻路径 P1；重路径 P3（且需先解决合规前置决策）**。

### 12.5 升级方向优先级与依赖顺序

| 优先级 | 方向 | 结论 | 主要代价 | 主要风险 |
|---|---|---|---|---|
| **P1** | 12.2 正式矢量边界 | 代码已就绪，缺数据 | 获取/核实边界数据 + 运行时接线 | 坐标系与边界质量；收紧后需比对差异 |
| **P1** | 12.4 移动端响应式 + 扫码入口（轻路径） | 高可行、可独立开工 | 样式与布局整改 | 需保持摄像头权限收口 |
| **P2** | 12.1 生成器独立成包 | 中高可行，被 schema 与打包边界卡住 | 多校 schema 对齐 + 打包设计 | 不得把认养人数据一起分发 |
| **P3** | 12.3 智能体化（仅加法） | 方向正确但被前置卡住 | 规划器 + 回退 + 工具契约 | 提示注入；写操作绝不能自动化 |
| **P3** | 12.4 小程序（重路径） | 成本高、合规前置未决 | 整体重写 + 主体资质 | 二次展示认养人信息的同意范围 |

**依赖顺序（硬约束）**：

```text
12.2 边界数据（校方 / 公开 GIS 授权）
        └─► 12.2 运行时接入 campus_at()（7 处调用方）
12.1 多校 schema 对齐（schools / school 外键 / brand）
        └─► 12.1 生成器打包独立化
§9   评测基线（加难例 + 补热图标注 + 排序指标）
        └─► §3 检索质量（reranker）
                └─► 12.3 智能体化（仅加法）
12.4 轻路径（响应式 + 扫码）—— 不依赖以上任何一项，可立即开工
12.4 重路径（小程序）—— 需先有"二次展示认养人信息"的合规结论
```

**一句话**：**先补前置（边界数据、多校 schema、评测基线），再做升级；唯一可以立刻开工的是移动端响应式 + 扫码入口。**
