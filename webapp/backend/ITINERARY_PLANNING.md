# 一日行程规划（itinerary）

面向"第一次来校"的用户：一句话即可得到上午 / 中午 / 下午三段式的完整游览方案，
并以**三种形式同时呈现**——文字行程、地图按 1→2→3 顺序标注的多点、相邻两点之间的步行路线。

典型提问：「我第一次来普陀校区，帮我规划一天」。

## 一、核心设计：骨架与文案分离

老师提出的三条硬约束——**三段都要有落点、中午必须是餐饮、点与点不折返**——如果交给
大模型自由编排无法稳定保证。因此：

| 职责 | 由谁负责 |
|---|---|
| 决定去哪些点、以什么顺序去 | **后端确定性算法**（`itinerary.py`） |
| 怎么用自然语言描述 | **大模型**（`resolve_llm()`，服务商由 `.env` 的 `LLM_PROVIDER` 显式选择：deepseek / chatecnu） |

结构正确由算法保证，语言体验由模型提供；大模型失败或超时时回退确定性模板文案，功能不中断。

## 二、边界与不变量

1. **不触碰热力图算法与缓存**：`scene_heatmaps.py`、`heatmap_cache/*.json`、`semantic_index.npz`
   一行不改、不重建。行程规划只读取既有排序结果（`rank_campus_places`），与 SAKDE 侧的演进解耦。
2. **不新增热力图场景**：`SCENE_IDS` 保持四类不变。
3. **响应契约只增不改**：既有 `choices` / `locations` / `ranked_places` / `heatmap` 结构不动，
   行程数据放在新增的顶层 `itinerary` 字段，且仅在命中行程意图时出现。
4. **意图判定用纯规则**（关键词 + 正则），不依赖句向量，因此在本机未启用语义检索时同样可用，
   单测也可完全离线运行。
5. **不新增任何依赖**：后端仍是 Flask + requests，前端仍是 Vue3 + Element Plus + 高德 JS API。
6. **只在 sakde 模式下接管**：行程与场景热图同属"新模式"能力，因此仅当请求带
   `recommendationMode: 'sakde'` 且命中行程意图时才生效；默认路径（常规导航）的行为与改动前
   完全一致。弱意图词（"刚来 / 初来 / 第一次来"）还必须配合时段线索（上午 / 中午 / 下午 /
   一天 / 半天…）才算行程意图，避免抢走"我刚来学校，想去图书馆"这类地点问句。

## 三、接口契约

`POST /api/chat` 命中行程意图时返回（其余字段与既有逻辑一致）：

```jsonc
{
  "choices": [{ "message": { "role": "assistant", "content": "<行程文案>" } }],
  "locations": [ /* kind = "itinerary_stop"，含 seq / period / periodLabel / reason / dwellMinutes */ ],
  "ranked_places": [],
  "recommendation_engine": "itinerary",
  "itinerary": {
    "title": "普陀校区一日游",
    "campus": "普陀",
    "fallback": false,          // true 表示大模型不可用，文案为确定性模板
    "stops": [                  // 按游览顺序，seq 从 1 起
      { "seq": 1, "period": "morning", "periodLabel": "上午", "name": "…",
        "lng": 0, "lat": 0, "campus": "普陀", "scene": "walk", "category": null,
        "subCategory": null, "reason": "…", "dwellMinutes": 90 }
    ],
    "legs": [                   // 相邻两站的通行段
      { "fromSeq": 1, "toSeq": 2, "mode": "walking", "distanceMeters": 174,
        "durationMinutes": 2, "fromName": "…", "toName": "…", "estimated": true }
    ],
    "skipped": [ { "period": "noon", "label": "中午", "reason": "no_candidate" } ]
  }
}
```

`mode` 为 `riding` 表示该腿超过步行阈值，前端据此不画步行线、改提示骑行或乘校车。

`legs[].estimated` 标记该腿的数字是否为**后端的平面直线估算**（默认 `true`，不依赖任何外部服务，
保证离线可用）。总规则是"**只有能核实的数字才允许出现在对话文案里**"：

- `estimated: true`（当前后端始终如此）：大模型上下文与兜底文案都不写距离/耗时数字，数字只出现在
  面板里，并由前端用 `AMap.Walking` 的真实算路结果覆盖；未被覆盖的腿面板会加"约"字。这样**气泡与
  面板不可能互相矛盾**（气泡里没有可矛盾的数字）。
- `estimated: false`（后端改用高德 Web 服务算过真实路线时）：文案可以写这些数字，前端**不得覆盖**，
  以保证两端一致。

行程文案只出现在 `choices[0].message.content`，`itinerary` 结构里不再重复一份——避免同一段
文本在响应里传两份、也避免前端出现"两份真相"。

前端契约见 `webapp/frontend/src/components/itineraryTypes.ts`。

**未命中行程意图或站点不足时不会出现 `itinerary` 字段**：站点不足（少于 3 站）会退回普通推荐
链路，并在响应里附带 `itinerary_status`（与既有 `heatmap_status` 同一范式），前端在对话末尾补
一句「行程提示：…」，避免用户以为系统答非所问。

## 四、编排算法

```
午/晚/下午候选  →  去重清洗  →  中午强制只留餐饮  →  三段顺序贪心最近邻串联  →  legs 计算
```

- **候选来源**（`server.py::_ITINERARY_PERIOD_QUERIES`）：上午取 `walk` + `photo`，中午取 `dining`
  （即 `canteen_pois.json` 的食堂点位），下午取 `flower_viewing` + `photo` + `study`。
  合成查询里**不写校区名**，校区一律由 `preferred_campus` 决定，避免与用户实际询问的校区冲突。
- **起点**：优先用用户定位（`ranking_location`）；没有定位时从上午首个候选起步。二者都保证
  后续站点按最近邻串联，因此不会来回折返。
- **名额分配**：上午最多 2 站、中午固定 1 站、下午最多 2 站；并为后续时段各预留 1 个名额，
  保证三段都能落到点，总站点 3–5 个。
- **降级**：某时段无候选 → 跳过并在 `skipped` 中给出原因，面板对应位置显示灰色虚线占位；
  相邻两站超过 `DEFAULT_MAX_WALK_METERS`（1200 m）→ 选不到阈值内候选时退化为最近的候选，
  该腿标记为 `riding`；总站点少于 3 个 → 返回 `None`，由调用方回退到普通推荐链路并附
  `itinerary_status` 说明原因；中午候选若"部分带类别且一条餐饮都没有"，退回未标注类别的候选，
  而不是把中午整体清空。

常量集中在 `itinerary.py` 顶部，便于调参与测试。

## 五、前端集成

| 位置 | 改动 |
|---|---|
| `components/itineraryTypes.ts` | 新增：与后端契约一一对应的类型 |
| `components/ItineraryPanel.vue` | 新增：竖向时间轴面板（三段卡片、序号徽章错峰入场、**每站之后紧跟该站出发的通行段**、空态/降级样式、卡片与序号均可键盘操作） |
| `views/chatbot.vue` | 消费 `data.itinerary`；`pickMapLocations` 放行 `itinerary_stop`；标记按 `第N站` 标注；新增 `drawItineraryRoute()` 逐段绘制步行路线；面板点击可定位站点或对单站发起导航；面板显示条件与当前校区绑定（`visibleItinerary`）；展示 `itinerary_status` 行程提示 |
| 真实路线校正（同上文件） | `legRouteInfo` 收下 `AMap.Walking` 回调里的真实距离/时长（**复用同一次算路，不增加请求**），`panelItinerary` 把它合并进面板数据并给出 `estimated` 标记 |

**与既有功能不冲突的三点处理**：

1. 行程路线使用**独立的 `AMap.Walking` 实例数组**（`itineraryWalkings`），清理时只清自己的，
   不会与既有单点导航（`walking`）互相清除；路线加红色描边，与单点导航的默认样式区分。
2. 标记标签按 `kind` 分支：既有 `ranked_place` 仍显示 `Top${rank}`，行程站点显示 `第${seq}站`。
3. 行程数据在渲染地图**之前**写入响应状态，因为绘制路线时要读 `legs` 判断哪些腿是骑行。

行程面板与热力图面板都在地图左上角同一位置，但两者互斥（后端一次只返回其一），不会同时出现。

面板只显示"与当前校区匹配"的行程：行程数据在切换校区后仍然保留（切回即恢复），但地图标记已被
按校区过滤，若面板继续显示就会出现"面板有内容、地图是空的"的不一致，因此显示层用
`visibleItinerary` 做同校区过滤。

通行段按**站点**而非按时段挂载：每条 leg 的 `fromSeq` 就是"出发那一站"，逐站渲染才能同时覆盖
同一时段内的连接与跨时段的连接。按"每段最后一站"挂载会丢掉段内连接（上午第 1→2 站）和最后一段
的末尾连接（下午第 4→5 站）。

## 六、验证结果

| 项目 | 结果 |
|---|---|
| `python -m unittest test_itinerary` | **34/34 通过**（意图判定、三段完整性、中午餐饮、去重、贪心顺序、阈值降级、缺失时段、站点不足回退、文案与契约） |
| `python -m unittest test_scene_heatmaps` | 22/22 通过（无回归） |
| `python -m unittest test_security` | 6/6 通过（无回归） |
| `npx vue-tsc --noEmit` | exit 0，零类型错误 |
| 浏览器端到端 | 实测「我第一次来普陀校区，帮我规划一天」→ `engine=itinerary`、5 站（上午 2 / 中午 1 / 下午 2）、5 个地图标记、面板 `stops=5 / legs=4 / skip=0`，四条通行标签齐全，对话区显示大模型生成的分段文案 |
| 接口回归（脚本实测） | 带 `sakde` → 返回 `itinerary`；不带模式 → 无 `itinerary`（常规路径不变，93 个打点）；「我刚来学校，想去图书馆」→ 不再被误判，正常回答图书馆 |
| 兜底路径（测试客户端 + 桩） | 行程站点不足 → 返回 `itinerary_status`；大模型文案失败 → `fallback=true` 且模板文案覆盖全部站点 |
| 真实路线校正（浏览器实测） | 同一次请求内对比后端估算与面板显示：`1→2 123m→326 米/4 分钟`、`2→3 174m→255 米/3 分钟`、`3→4 119m→114 米/2 分钟`、`4→5 111m→174 米/2 分钟`，均无"约"字，确认为高德真实算路结果 |
| 气泡与面板一致性（浏览器实测） | 同一次请求中：后端四条腿均为 `estimated=true`，气泡文本里 `步行…米` 与 `米` 的匹配数**均为 0**，面板显示上述真实值；`fallback=false`，即大模型文案正常生成 |

**耗时实测**（本机，语义检索关闭）：普通场景问答约 25 s，行程问答约 32 s。
行程多出的约 7 s 来自 6 次候选排序；**大模型调用次数没有增加**（仍为 1 次/请求）。

> 注：本机未设 `SEMANTIC_ENABLED=false` 时，处理第一个走语义检索的问答会让进程崩溃
> （`0xC0000005`，既有问题，与本次改动无关），因此端到端验证是用该环境变量启动的。

## 七、已知限制与后续

1. **候选排序次数**：一个行程请求会做 6 次 `rank_campus_places`。若后续语义检索耗时上升，
   可合并为每时段一次查询或加缓存。
2. **开场点位固定**：三段的首站分别取自散步/餐饮/赏花拍照场景，尚无"按用户兴趣加权"的机制。
3. **对话文案不含距离数字**：后端给的是直线估算，与面板（高德真实路线）天然不一致，因此文案
   （大模型上下文与确定性兜底文案统一口径）一律不写距离/耗时数字，数字只在面板出现。若希望文案
   里也能有真实数字，需要后端改用高德 Web 服务算路（`AMAP_WEB_SERVICE_KEY`，与前端 JS API key
   不是同一种 key）后再生成文案，届时把 `legs[].estimated` 置为 `false` 即可，前端会自动以它为准。
4. **系统代理会让后端调不通大模型**：Clash 等工具把 Windows 系统代理注册成
   `https://127.0.0.1:7897` 时，`requests` 会把它当成 TLS 代理，抛 `SSLEOFError`，对外表现为
   "AI 服务请求失败"——**整站问答都会挂，不只是行程**。已改为默认直连
   （`proxies={'http': None, 'https': None}`）；确需代理时用 `LLM_HTTP_PROXY` 显式配置。
5. **`riding` 腿仍为估算且不画线**：这类腿没有可用的步行结果，面板按 `estimated` 加"约"字提示；
   若要让它们也显示真实里程，可换 `AMap.Riding`（骑行）或 `AMap.Transfer`（公交/校车）查询。
6. **跨校智能体**（老师第二个建议）属后续阶段，与本次模块解耦：目标是把"人工找点"变成自动化，
   使新学校产出与当前效果类似；已定方向为**单校试点**，数据来源允许高德 POI + 大模型联网检索
   公开资料 + 网页采集。本次不实现。
